# Independent-agent hostile review — G3 source verification, 15 November 2026

Source: Gemini's audit supplied to the project by its author (review text contains no executable exploit or independently verified line references). This note separates observed source behavior from threat hypotheses. The current reviewed base is merged PRs #447–#450, with this note's branch applied.

## Conclusions and limits

1. **Ed25519 replay** — Current `koru_ed25519_permit.py` includes issuer, full event digest, context digest, authority and expiration. It lacks a separate `nonce` field, but the signed event carries both `event_id` and `idempotency_key` bound to its digest, and the SQLite admission journal rejects duplicate identity/idempotency keys. The effect table uses the event ID as primary key, with replay returning `already_dispatched`; actual marker creation uses an exclusive hashed event ID path. Thus a second effect on the same ID is blocked or idempotent in the selected pilot. Do **not** claim that a nonce is universally unnecessary: cross-service operations, issuer key compromise, independent-effect types and future issuance policies need their own replay threat model.
2. **Revocation TOCTOU** — `SyntheticEffectGate.dispatch_synthetic` rechecks hold, generation, signed expiry, authority revocation, exact journal record and synthetic witness in an immediate transaction. `ProtectedFilesystemSink.apply_marker` wraps the effect and fsync in the gate lock. PR #450 introduced opt-in cooperative POSIX `flock` for separate controller processes. This is a meaningful mitigation **only when every privileged writer/control process uses the same lock inode**; uncooperative privileged code or alternate DB/FS write access is not prevented.
3. **SQLite** — `PilotGate._transaction` explicitly executes `BEGIN IMMEDIATE`; the default deferred-transaction stale-snapshot counterexample does not directly describe this code path. Never infer entire-service atomicity, however: SQLite and external filesystem marker durability remain separate.
4. **Descriptor and symlink threats** — The lock file uses `O_NOFOLLOW` and (where available) `O_CLOEXEC`; effect directory uses `O_DIRECTORY | O_NOFOLLOW`, marker uses directory-relative `O_EXCL | O_NOFOLLOW`, and prior markers are opened and checked through directory fds. The current repository does **not** inventory every possible inherited descriptor from an actual deployment or enforce platform-wide seccomp/namespace policy. The broker has no production startup or container deployment configuration. Treat fd inheritance and alternate path privilege as **open release gates**, not source-proven exploits at particular lines.
5. **Lean/runtime** — Existence of formal G1/G2/G3 theorems in the repository and green Lean builds does **not** establish their invariants for every running physical action. The original six X3 duties and Complete Koru whole-state/source correspondence require independently grounded real-world evidence; source checks currently use synthetic fixtures. The audit's phrase “six X3 duties establish no action may execute” must be read as a desired formal-to-runtime contract, not a deployed universal invariant.

## Concrete source-verified bypass repaired in this branch

Previously `koru_broker.py` allowed `dispatch` even when `effect_sink` was configured. An authorized caller could first admit a valid event, then call `dispatch`, which added the `synthetic_effects` record **without creating the corresponding actual marker**. `reconcile_report()` then correctly saw a pending real effect. Under PR #449's fail-closed effect ordering, that pending item could block other effects until recovery. This was an unintended client-exposed synthetic-only route in a real-marker configuration.

The broker now refuses `dispatch` with `effect_route_required` **when a real marker sink is configured**. `effect_marker` still calls the full gate and file sink; the synthetic-only research broker (no effect sink) retains `dispatch` for its tests. The Linux separate-UID adversarial test asserts the denial and exercises correct real-marker authorized and expired flows.

## Remaining launch prerequisites

No production service is deployed. Before real applications: establish dedicated least-privilege principals for sink, controller and issuer; prevent untrusted code from inheriting any privileged writable fd; require hard OS effect-path isolation, signed/attested privileged commands and independent trusted time; bind rights and consent evidence to actual subjects/events; enumerate complete effect capabilities and all alternative writes; test crash/kill and reliable recovery. No one audit result alone proves universal physical coverage.
